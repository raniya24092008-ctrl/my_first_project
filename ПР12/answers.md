## 1. В чём разница между `event.preventDefault()` и `event.stopPropagation()`?

Это два разных механизма, и они не заменяют друг друга.

| | `preventDefault()` | `stopPropagation()` |
|---|---|---|
| Что делает | Отменяет **стандартное действие браузера**, привязанное к событию | Останавливает **распространение события** по дереву DOM |
| На что влияет | На поведение: переход по ссылке, отправку формы, прокрутку, сохранение страницы | На порядок вызова обработчиков |
| Что меняет в объекте события | `event.defaultPrevented === true` | Ничего (событие просто не идёт дальше) |
| Когда не работает | Если `event.cancelable === false` (например, событие `scroll` нельзя отменить) | Если событие не всплывает (`mouseenter`, `focus`, `load`) |

```js
// 1. Ссылка не перейдёт по адресу, но событие продолжит всплывать к родителям
link.addEventListener('click', (event) => {
  event.preventDefault();
});

// 2. Событие не дойдёт до родительских обработчиков, но браузер выполнит действие
button.addEventListener('click', (event) => {
  event.stopPropagation();
});
```

**Когда что использовать:**

- `preventDefault()` — когда нужно заблокировать именно поведение браузера: отменить переход по ссылке-заглушке, взять отправку формы на себя и делать её через `fetch`, запретить сохранение страницы по `Ctrl+S` в своём редакторе, отменить контекстное меню в кастомном приложении.
- `stopPropagation()` — когда нужно изолировать обработчик: клик внутри модального окна не должен доходить до обработчика на `document`, который закрывает окно; клик по кнопке внутри карточки не должен одновременно «выбирать» карточку.

Дополнительно существует `stopImmediatePropagation()` — он останавливает распространение **и** блокирует остальные обработчики этого же события на том же элементе, зарегистрированные позже.

В работе оба метода применены осознанно: в задании 4 для ссылки и формы используется `preventDefault()`, а в задании 2 — `preventDefault()` для комбинаций `Ctrl+S`, `Alt+C`, `Shift+A`. При этом обработчики не «глушат» событие целиком: остальная логика страницы продолжает работать.

## 2. Как работает делегирование событий и какие преимущества оно даёт?

**Идея:** вместо обработчика на каждом элементе вешается **один** обработчик на общий родитель. Так как событие всплывает, оно доходит до родителя, а конкретный элемент определяется по `event.target`.

```js
list.addEventListener('click', (event) => {
  const deleteButton = event.target.closest('.delete');
  if (deleteButton) {
    deleteButton.closest('.item').remove();
    return;
  }

  const item = event.target.closest('.item');
  if (item) item.classList.toggle('selected');
});
```

Алгоритм:

1. Событие возникает на самом глубоком элементе (`event.target`).
2. Всплывает до контейнера, где висит обработчик (`event.currentTarget`).
3. Внутри обработчика через `target.closest('.item')` находится нужный элемент.
4. Действие выполняется только если найденный элемент действительно принадлежит контейнеру (проверка `list.contains(target)`).

**Преимущества:**

- **Работает для динамических элементов.** Новые `.item` из `addNewItem()` сразу поддерживают клики — переподключать обработчики не нужно (это проверяется тестом).
- **Меньше обработчиков.** 1000 строк списка — не 1000 (или 2000) функций, а одна. Меньше памяти и быстрее инициализация.
- **Проще поддерживать и удалять.** Один `removeEventListener` снимает всю логику — не нужно обходить DOM и чистить каждый элемент.
- **Нет утечек при удалении элементов.** Обработчики не «висят» на удалённых узлах.

**Ограничения:**

- Событие должно всплывать. `mouseenter`, `mouseleave`, `focus`, `blur`, `load`, `scroll` не всплывают — для них делегирование не работает напрямую (используют `mouseover`/`mouseout`, `focusin`/`focusout` или фазу перехвата).
- Нужны дополнительные проверки `closest()` и `contains()` — чуть больше кода в одном месте.
- Сложнее отлаживать: обработчик один, и точка входа не очевидна из разметки.

## 3. Какие фазы жизненного цикла события существуют и как они влияют на порядок обработчиков?

Событие проходит три фазы (`event.eventPhase`):

1. **Capturing (перехват, фаза 1)** — от `window` → `document` → … → родителя цели. Обработчики, добавленные с `{ capture: true }` (или третьим аргументом `true`), срабатывают сверху вниз.
2. **Target (цель, фаза 2)** — на самом элементе-источнике. Здесь срабатывают обработчики, навешенные на целевой элемент (порядок — порядок регистрации).
3. **Bubbling (всплытие, фаза 3)** — от цели вверх к `document` и `window`. Обработчики без флага capture срабатывают снизу вверх.

```js
outer.addEventListener('click', () => log('capture'), true);  // фаза 1
inner.addEventListener('click', () => log('target'));         // фаза 2
outer.addEventListener('click', () => log('bubble'));         // фаза 3

inner.click(); // capture → target → bubble
```

Порядок в этом примере проверяется тестом «порядок обработчиков: capturing → target → bubbling».

На что это влияет на практике:

- `stopPropagation()` в фазе перехвата не даст событию дойти до цели вообще.
- Глобальные «перехватчики» (логирование, аналитика, закрытие выпадающих меню) удобно вешать в capturing-фазе: они увидят событие раньше прикладных обработчиков и смогут его отменить.
- Не все события всплывают: `focus`, `blur`, `mouseenter`, `mouseleave`, `load`, `scroll` — только на самом элементе. Для делегирования берут их всплывающие аналоги.
- `addEventListener(type, handler, options)` поддерживает `capture`, `once`, `passive`, `signal` — всё это настраивается отдельно для каждой подписки.

## 4. Разница между `event.target` и `event.currentTarget`

| | `event.target` | `event.currentTarget` |
|---|---|---|
| Что это | Элемент, **на котором произошло событие** (источник) | Элемент, **на котором сейчас выполняется обработчик** |
| Меняется ли при всплытии | Нет, всегда один и тот же | Да, на каждом новом обработчике новый |
| Где особенно полезен | Делегирование: определить, по чему именно кликнули | Работа с элементом, к которому привязан обработчик: `classList`, `dataset`, `style` |
| После завершения обработки | Остаётся | Становится `null` |

```html
<ul id="list">
  <li class="item">Текст <button class="delete">×</button></li>
</ul>
```

```js
list.addEventListener('click', (event) => {
  console.log(event.target.tagName);        // BUTTON — кликнули по крестику
  console.log(event.currentTarget.tagName); // UL — обработчик на списке
  event.currentTarget.classList.add('active'); // меняем сам список
  event.target.closest('.item').remove();      // удаляем конкретный элемент
});
```

**Правило выбора:**

- `currentTarget` — когда действие относится к элементу, на котором висит обработчик (подсветить контейнер, добавить класс самому блоку, прочитать его `data-*`).
- `target` — когда нужно понять, куда именно попал пользователь (делегирование, drag-and-drop, проверка «клик был внутри или снаружи»).

Важная деталь: в обработчике, сохранённом в переменной и вызванном позже, `event.currentTarget` уже `null` — поэтому внутри асинхронных колбэков (`setTimeout`, `await`) ссылку на элемент надо сохранять в локальную переменную. В работе так и сделано в `handleBasicClick`: `const button = event.currentTarget;` до `setTimeout`.

## 5. Как создать и запустить кастомное событие? Какие параметры принимает `CustomEvent`?

Кастомное событие создаётся конструктором `CustomEvent` и отправляется через `dispatchEvent()` на любом узле DOM (или на `document`/`window`).

```js
// Создание
const customEvent = new CustomEvent('customAction', {
  detail: { message: 'Привет от кастомного события!', timestamp: Date.now() },
  bubbles: true,      // всплывает ли событие
  cancelable: true,   // можно ли отменить через preventDefault()
  composed: false     // выходит ли событие за пределы shadow DOM
});

// Подписка
document.addEventListener('customAction', (event) => {
  console.log(event.detail.message); // данные лежат в detail
});

// Запуск
document.dispatchEvent(customEvent);
```

Параметры конструктора:

| Параметр | Значение по умолчанию | Назначение |
|---|---|---|
| `type` (первый аргумент) | — | Имя события, строка |
| `detail` | `null` | Любые данные, передаваемые вместе с событием (объект, массив, примитив) |
| `bubbles` | `false` | Всплывает ли событие |
| `cancelable` | `false` | Можно ли отменить стандартное действие |
| `composed` | `false` | Проходит ли событие через границу shadow DOM |

Особенности:

- В `detail` можно передать **любой** объект, включая функции и ссылки на DOM-элементы — это обычное JavaScript-значение, а не сериализуемые данные.
- `dispatchEvent()` **синхронный**: обработчики выполняются сразу, до возврата из вызова.
- Возвращаемое значение `dispatchEvent()` — `false`, если событие было отменено через `preventDefault()`.
- У созданного вручную события `event.isTrusted === false` — браузер не считает его действием пользователя, поэтому некоторые действия (например, полноэкранный режим) с ним недоступны.
- Для событий без данных достаточно `new Event('customName')`; `CustomEvent` нужен именно из-за `detail`.

В практической работе (задание 5) `triggerCustomEvent()` отправляет `customAction` с `detail.message`, а `handleCustomEvent()` читает `event.detail` и выводит его в `#custom-output`. Три независимых обработчика демонстрируют, что на одно событие можно подписать сколько угодно функций: каждая получит один и тот же объект события.

## 6. Что такое debounce и throttle? Где их применять?

Обе техники ограничивают частоту вызовов, но по-разному.

**Debounce** — вызов выполняется **один раз после паузы**: каждый новый вызов сбрасывает таймер. Если события идут непрерывно, функция не вызывается вообще, пока они не прекратятся.

```js
function createDebounce(func, delay) {
  let timerId = null;
  return function debounced(...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => func.apply(this, args), delay);
  };
}
```

**Throttle** — вызов выполняется **не чаще одного раза за интервал**: первый вызов срабатывает сразу, остальные в течение интервала игнорируются (либо выполняются в конце окна — trailing-вызов).

```js
function createThrottle(func, interval) {
  let lastCall = 0;
  return function throttled(...args) {
    const now = Date.now();
    if (now - lastCall >= interval) {
      lastCall = now;
      func.apply(this, args);
    }
  };
}
```

Сравнение на серии быстрых событий (за 1 секунду):

| | Обычная функция | Debounce 300 мс | Throttle 300 мс |
|---|---|---|---|
| Вызовов за серию 20 событий | 20 | 1 (после паузы) | 3–4 (по одному на окно) |
| Реакция | на каждое событие | только на «финал» | регулярно, но с ограничением |

**Где что эффективнее:**

- Debounce: поиск с автодополнением по вводу (запрос только когда пользователь перестал печатать), валидация поля, автосохранение черновика, изменение размера окна (`resize`) с пересчётом раскладки, отправка аналитики по «завершённому» действию.
- Throttle: обработка `scroll` (параллакс, «липкая» шапка, бесконечная прокрутка), `mousemove`/`pointermove` (кастомный курсор, drag), частые клики (защита от двойного заказа), обновление координат в играх и графиках, ограничение частоты запросов к API.

Дополнительно различают режимы: `leading` (вызов в начале окна), `trailing` (в конце), оба сразу. В работе реализован throttle с leading + trailing: быстрый клик срабатывает сразу, а последний вызов в серии не теряется — выполняется в конце интервала. У debounce добавлены `cancel()` и `pending()` для отмены отложенного вызова.

## 7. Какие методы есть для удаления обработчиков и почему это важно?

Основной способ — `removeEventListener(type, handler, options)`.

```js
function onClick(event) { /* ... */ }

button.addEventListener('click', onClick);
button.removeEventListener('click', onClick); // снимает обработчик
```

Ключевые правила:

- Нужна **та же ссылка** на функцию. `removeEventListener('click', () => {})` ничего не удалит: это уже другая функция.
- Должны совпадать `type` и флаг `capture`. Если слушатель добавлен с `{ capture: true }`, удалять нужно тоже с `{ capture: true }`.
- Опции `once` и `passive` при удалении не важны, важен только `capture`.

Современная альтернатива — `AbortController`: один сигнал снимает сразу группу обработчиков.

```js
const controller = new AbortController();
const { signal } = controller;

window.addEventListener('scroll', onScroll, { signal, passive: true });
window.addEventListener('resize', onResize, { signal });

controller.abort(); // снимает оба обработчика
```

Также существует `element.onclick = null` — но это работает только для обработчиков, назначенных через свойство, и снимает их целиком.

**Почему важно удалять обработчики:**

- **Утечки памяти.** Обработчик держит ссылку на элемент и замыкание. Если элемент удалён из DOM, но на нём остался слушатель, сборщик мусора не освободит память. В SPA со временем это приводит к замедлению и падению вкладки.
- **Дублирование логики.** При повторном монтировании компонента без снятия обработчиков один клик вызывает функцию дважды, трижды и т.д.
- **Устаревшие данные (stale closures).** Обработчик «помнит» старое состояние; после обновления данных он продолжает работать со старыми значениями.
- **Ошибки после удаления элемента.** Обработчик на глобальном объекте обращается к удалённому узлу и падает с `null is not an object`.
- **Лишняя нагрузка.** «Мёртвые» слушатели всё равно вызываются при каждом событии и тратят время.

Практические приёмы: снимать обработчики при уходе со страницы/размонтировании компонента, для одноразовых действий использовать `{ once: true }`, для глобальных — `AbortController`, в `setInterval`/`setTimeout` обязательно вызывать `clearInterval`/`clearTimeout` (в работе это делает `stopTimer()`).

## 8. Как обрабатывать ошибки загрузки ресурсов и какие события для этого используются?

Для разных ресурсов набор событий отличается, но принцип один: успех — `load`, неудача — `error`.

```js
const image = new Image();
image.addEventListener('load', () => console.log('загружено', image.naturalWidth));
image.addEventListener('error', () => console.log('не удалось загрузить'));
image.src = 'https://example.com/photo.jpg';
```

| Ресурс | События | Особенности |
|---|---|---|
| `<img>` | `load`, `error` | `load` даёт `naturalWidth`/`naturalHeight`; `error` не содержит деталей (код/причина недоступны) |
| `<script>` | `load`, `error` | Позволяет включить резервный CDN |
| `<link rel="stylesheet">` | `load`, `error` | `error` надёжнее ловить в capturing-фазе |
| `<video>`/`<audio>` | `loadstart`, `progress`, `loadedmetadata`, `canplay`, `error` | Есть `MediaError` с кодом |
| XHR | `loadstart`, `progress`, `load`, `error`, `abort`, `timeout`, `loadend` | Плюс `xhr.status` и `xhr.statusText` |
| `fetch` | промис + `response.ok` | Сетевые ошибки — reject, HTTP-ошибки — не reject, нужна проверка `ok` |

Важные нюансы:

- Событие `error` у ресурсов **не всплывает**. Чтобы поймать его глобально, слушатель ставится на `window` с флагом capture:
  ```js
  window.addEventListener('error', (event) => {
    if (event.target && event.target.tagName === 'IMG') {
      event.target.src = '/img/fallback.png';
    }
  }, true);
  ```
- У `<img>` **нет** событий `loadstart` и `loadend` — они есть у XHR, `fetch` и медиаэлементов. В задании 6 эти события зарегистрированы и `loadstart` отправляется вручную, а `loadend` — из обработчика `load`, что показывает понимание разницы.
- `error` не сообщает причину. Для диагностики нужны сетевые инструменты DevTools: 404, 403, CORS, таймаут.
- Полезно добавлять **таймаут**: если ответ не пришёл за N секунд, считать загрузку неудачной (`setTimeout` + `clearTimeout` в обработчике). Это реализовано в `simulateLoadError()`.
- Для отмены загрузки: `fetch` + `AbortController`, у `<img>` — смена `src` или удаление элемента.
- Заглушка вместо «битой» картинки — обязательный элемент UX: пользователь должен видеть текст ошибки, а не пустое место.

## 9. Чем `addEventListener` отличается от прямого назначения `onclick`?

| | `addEventListener` | `element.onclick = fn` |
|---|---|---|
| Несколько обработчиков на одно событие | Да, все вызываются по порядку | Нет, новый перезаписывает предыдущий |
| Снятие обработчика | `removeEventListener` с той же функцией | `element.onclick = null` |
| Фаза перехвата | Да (`{ capture: true }`) | Нет (только фаза цели и всплытие) |
| Опции `once`, `passive`, `signal` | Да | Нет |
| Прозрачность | Список слушателей виден в DevTools | Виден как свойство |
| Ошибки в обработчике | Не ломают другие обработчики события | Свойство остаётся, но при следующем присваивании теряется |
| `return false` | Ничего не делает | Отменяет стандартное действие (историческое поведение) |
| `this` внутри | Элемент (для обычной функции) | Элемент |
| Inline `onclick="..."` в HTML | — | Требует `unsafe-inline` в CSP, смешивает разметку и логику |

```js
// Перезапись: сработает только второй обработчик
button.onclick = () => console.log('первый');
button.onclick = () => console.log('второй');

// Оба обработчика работают
button.addEventListener('click', () => console.log('первый'));
button.addEventListener('click', () => console.log('второй'));
```

**Вывод:** `addEventListener` — стандарт для прикладного кода: он предсказуем, поддерживает несколько подписчиков, фазы и опции, легко снимается. Свойства `onclick`/`onkeydown` уместны для простых одноразовых случаев и для намеренной замены единственного обработчика, а inline-атрибуты в HTML в современном коде не используются из-за CSP и проблем с поддержкой.

## 10. Как оптимизировать производительность при большом количестве событий?

1. **Делегирование вместо сотен обработчиков.** Один слушатель на контейнер вместо обработчика на каждом элементе — меньше памяти, быстрее инициализация, автоматическая поддержка новых узлов.
2. **Throttle и debounce для «частых» событий.** `mousemove`, `scroll`, `resize`, `input`, `pointermove` генерируются десятки раз в секунду. Ограничение частоты снижает число вызовов на порядки.
3. **`passive: true` для `touchstart`/`touchmove`/`wheel`/`scroll`.** Браузер не ждёт обработчик перед прокруткой — исчезает «залипание» скролла:
   ```js
   window.addEventListener('scroll', onScroll, { passive: true });
   ```
4. **Не читать layout в цикле.** Чередование записи и чтения (`style.x = ...; offsetHeight; style.y = ...`) вызывает layout thrashing. Сначала все чтения, затем все записи, а лучше — через `requestAnimationFrame`.
5. **`requestAnimationFrame` для визуальных обновлений.** Не чаще одного обновления на кадр (~16,7 мс при 60 Гц).
6. **Наблюдатели вместо событий.** `IntersectionObserver` (появление в зоне видимости) и `ResizeObserver` (изменение размера) дешевле, чем `scroll` + `getBoundingClientRect()`.
7. **Кэшировать ссылки и данные.** `querySelector` в обработчике на каждое событие — лишняя работа. Ссылки на элементы и «дорогие» вычисления сохраняются один раз или инвалидируются осознанно.
8. **Правильные обработчики в циклах.** Использовать `let`/`const` (у каждой итерации своя переменная) или `data-*` атрибуты; не создавать замыкания на `var`.
9. **`{ once: true }` для одноразовых действий** — браузер сам удалит слушатель, меньше ручной очистки.
10. **Снимать обработчики при размонтировании.** `removeEventListener` или один `AbortController` на компонент — против утечек памяти.
11. **Не злоупотреблять `stopPropagation()`.** Он ломает делегирование и заставляет дублировать обработчики; чаще достаточно проверки `event.target`/`closest()`.
12. **Виртуализация длинных списков.** Для таблиц на 10 000 строк рендерятся только видимые — событий становится на порядки меньше.
13. **Замерять, а не угадывать.** DevTools → Performance: смотреть на длинные задачи (Long Tasks), число вызовов обработчиков и принудительные пересчёты стилей.

## Итог

Обработка событий — это не только «повесить onclick». Устойчивый код получается, когда:

- обработчики **делегируются** на контейнер, а не размножаются по элементам;
- стандартное поведение отменяется **точечно** (`preventDefault`), а распространение — осознанно (`stopPropagation`);
- данные передаются через **`CustomEvent.detail`**, а не через глобальные переменные;
- частые события проходят через **debounce/throttle**, а слушатели **снимаются** при удалении элементов;
- ошибки загрузки **обрабатываются** и показываются пользователю;
- синтетические события (`dispatchEvent`) используются в **тестах** — это позволяет проверять обработчики без ручных кликов.
