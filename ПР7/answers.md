# Практическая работа №7. Вёрстка и валидация форм

## Ответы на вопросы для самоконтроля

## 1. Какие HTML5-атрибуты используются для клиентской валидации и какую функциональность они предоставляют?

**Ответ:** Основные атрибуты:

| Атрибут | Что делает |
|---|---|
| `required` | поле нельзя оставить пустым |
| `minlength` / `maxlength` | минимальная и максимальная длина текста |
| `min` / `max` / `step` | границы и шаг для чисел и дат |
| `pattern` | проверка значения регулярным выражением |
| `type` (`email`, `tel`, `url`, `number`, `date`) | проверка формата и подходящая клавиатура на телефоне |
| `multiple` | несколько значений (например, несколько email) |

Если ограничение нарушено, браузер сам блокирует отправку формы и показывает подсказку. Кроме того, поля получают псевдоклассы `:valid`, `:invalid`, `:required`, `:in-range`, и их можно стилизовать. В моей работе, например, у имени стоят `required minlength="2" maxlength="50"`, а у даты рождения `min` и `max`.

## 2. В чем разница между novalidate атрибутом формы и отключением валидации через JavaScript?

**Ответ:** `novalidate` это HTML-атрибут формы. Он отключает только автоматическую проверку и всплывающие подсказки браузера при отправке. Сами атрибуты `required`, `pattern` и остальные остаются в разметке, и их можно проверить из JS через `checkValidity()` и `validity`. Именно так сделано у меня: у формы стоит `novalidate`, а ошибки я вывожу своим оформлением.

Если же в JavaScript вызвать `e.preventDefault()` на событии `submit`, то отправка просто останавливается, а проверка сама по себе не отключается и не заменяется. Если не вызывать проверку полей, то форма отправится с любыми данными. Важно помнить, что JS можно отключить или обойти, поэтому проверка на стороне клиента нужна только для удобства, а данные всё равно нужно проверять на сервере.

## 3. Как правильно связать `<label>` с полем ввода и почему это важно для доступности?

**Ответ:** Есть два способа. Первый это атрибут `for`, значение которого равно `id` поля:

```html
<label for="email">Email</label>
<input type="email" id="email" name="email">
```

Второй это обернуть поле в `<label>` (так у меня сделаны radio и checkbox).

Это важно, потому что:

- скринридер зачитывает подпись при попадании в поле, и слепой человек понимает, что нужно ввести;
- клик по подписи ставит курсор в поле или переключает чекбокс, то есть область нажатия больше (удобно на телефоне);
- голосовое управление может обращаться к полю по названию.

Плейсхолдер подпись не заменяет, потому что он исчезает при вводе и хуже читается скринридерами.

## 4. Какие типы полей input наиболее подходят для разных видов данных (email, телефон, пароль и т.д.)?

**Ответ:**

| Данные | Тип | Что даёт |
|---|---|---|
| Имя, фамилия | `text` | обычный текст |
| Электронная почта | `email` | проверка формата, на телефоне клавиатура с `@` |
| Телефон | `tel` | цифровая клавиатура (формат нужно проверять через `pattern`) |
| Пароль | `password` | символы скрыты |
| Число | `number` | `min`, `max`, `step` |
| Дата | `date` | календарь и ограничение диапазона |
| Сайт | `url` | проверка адреса |
| Один из нескольких вариантов | `radio` или `select` | выбор одного |
| Несколько вариантов или согласие | `checkbox` | выбор нескольких |
| Длинный текст | `textarea` | многострочное поле |

Правильный тип экономит код: браузер сам проверяет формат и подбирает клавиатуру.

## 5. Как работает валидация с помощью pattern атрибута и в каких случаях его следует использовать?

**Ответ:** В `pattern` пишется регулярное выражение, с которым сравнивается всё значение поля целиком (начало и конец проверяются автоматически). Если значение не подходит, у поля срабатывает `validity.patternMismatch`, и поле становится невалидным. Пустое значение `pattern` не проверяет, этим занимается `required`. Работает только для текстовых типов (`text`, `tel`, `email`, `password`, `search`, `url`).

Использовать стоит, когда нужен особый формат: телефон, код, логин, почтовый индекс, сложность пароля. Для обычной почты лучше `type="email"`. Пример пароля из работы:

```html
<input type="password" pattern="^(?=.*[a-z])(?=.*[A-Z])(?=.*\d).+$" minlength="8">
```

Он требует хотя бы одну строчную, одну заглавную латинскую букву и цифру. Слишком сложные регулярки делать не стоит, а понятное сообщение об ошибке нужно показывать самой, потому что браузер пишет общую фразу.

## 6. Какие события JavaScript используются для реализации валидации в реальном времени и почему?

**Ответ:**

- `blur` срабатывает, когда пользователь ушёл из поля. Здесь показываем ошибку, потому что ругаться на человека, пока он ещё печатает, неприятно.
- `input` срабатывает при каждом изменении значения. Здесь, если ошибка уже показана, проверяем заново, чтобы она исчезла сразу после исправления. Также на нём работают счётчик символов и подсказки к паролю.
- `change` срабатывает при переключении чекбоксов и списков. Так я проверяю чекбокс соглашения.
- `submit` проверяем все поля перед отправкой и отменяем отправку через `e.preventDefault()`, если есть ошибки.
- `reset` срабатывает при очистке формы, нужно убрать ошибки.

Такое сочетание удобнее всего: ошибка появляется, когда человек закончил ввод, а пропадает сразу при исправлении.

## 7. Как обеспечить доступность сообщений об ошибках для пользователей скринридеров?

**Ответ:**

- Показывать ошибку **текстом** рядом с полем, а не только красной рамкой (цвет могут не различать).
- Контейнеру сообщения добавить `aria-live="polite"` (или `role="alert"`), чтобы скринридер зачитал текст, когда он появляется.
- Связать поле с сообщением через `aria-describedby="emailError"`, чтобы при фокусе зачитывалась и ошибка.
- Ставить полю `aria-invalid="true"`, когда оно невалидно.
- При отправке с ошибками переводить фокус на первое неверное поле.
- Обязательные поля отмечать атрибутом `required` и звёздочкой (и объяснять смысл звёздочки).
- Итоговое сообщение («форма отправлена» или «исправьте ошибки») выводить в блоке с `role="status"`.

В моей работе всё это сделано.

## 8. В чем преимущества использования fieldset и legend для группировки полей формы?

**Ответ:** `fieldset` объединяет связанные поля в смысловую группу, а `legend` даёт этой группе название.

- Скринридер при переходе по полям зачитывает название группы, поэтому видно, к чему относится поле (особенно важно для групп radio и checkbox: вопрос плюс варианты).
- Форма делится на понятные блоки («Личная информация», «Безопасность», «Дополнительная информация»), и пользователю проще её заполнять.
- Если поставить `disabled` на `fieldset`, то отключатся сразу все поля внутри.
- Группа получает стандартную рамку, которую легко стилизовать.

У меня три `fieldset` для основных блоков, а группы radio и checkbox оформлены через `role="radiogroup"` и `role="group"` с `aria-labelledby`.

## 9. Как реализовать кастомную валидацию для сложных случаев (например, подтверждение пароля)?

**Ответ:** Для таких случаев используется метод `setCustomValidity(сообщение)`. Если передать непустую строку, поле считается невалидным (`validity.customError`), а пустая строка снимает ошибку. Пример из работы:

```js
function checkPasswordMatch() {
    const mismatch = confirmPassword.value !== '' &&
                     confirmPassword.value !== password.value;
    confirmPassword.setCustomValidity(mismatch ? 'Пароли не совпадают' : '');
}
```

Эту функцию нужно вызывать при каждой проверке подтверждения и когда меняется основной пароль. Так же можно проверить возраст (не младше 18 лет), зависимость одного поля от другого или занятость логина (проверка через запрос к серверу).

## 10. Какие методы CSS используются для визуального отображения состояний валидности/невалидности полей?

**Ответ:**

- Псевдоклассы `:valid`, `:invalid`, `:required`, `:optional`, `:in-range`, `:out-of-range`.
- `:focus` и `:focus-visible` для фокуса, `:checked` для переключателей.
- `:placeholder-shown`, чтобы пустое поле не подсвечивалось ошибкой заранее: `input:invalid:not(:focus):not(:placeholder-shown)`.
- Класс `.error`, который добавляет JavaScript, когда нужна более гибкая логика (например, пароли не совпадают).
- Изменение `border-color`, `background-color` и `box-shadow`, значки через `::before` и `::after`, анимация `@keyframes shake` для встряхивания неверного поля.

Пример из работы:

```css
.form-group input:invalid:not(:focus):not(:placeholder-shown) {
    border-color: var(--color-error);
}
.form-group input:valid:not(:focus):not(:placeholder-shown) {
    border-color: var(--color-success);
}
```
